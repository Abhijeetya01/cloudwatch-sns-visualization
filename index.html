      This architecture detects and notifies. It does not reduce CPU utilization or repair the instance. Automatic remediation or scaling needs extra configuration (for example EC2 alarm actions, Auto Scaling policies, or EventBridge with Lambda/Systems Manager).
      
      
      Cloud Support Engineer troubleshooting points
      
      
        
        
      • INSUFFICIENT_DATA: check the instance is running, the metric dimension is the right InstanceId, the Region matches, and the alarm period is not shorter than the metric interval (5 min basic monitoring).
        • 
        
      • No email received: confirm the SNS subscription is "Confirmed" (check spam), the topic is set as the action for the ALARM state, the topic access policy allows CloudWatch to publish, and the topic is in the same Region.
        • 
        
      • Alarm state flapping: tune period, evaluation periods, and datapoints-to-alarm so short spikes do not page you.
        • 
        
      • High CPU is not always a failure: compare with status checks, application logs, and traffic before acting.
        • 
        
      • Use alarm history: the CloudWatch alarm History tab shows each state change and whether actions ran.
        • 
        
      • Basic vs detailed monitoring: 5-minute metrics by default; 1-minute detailed monitoring may incur charges.
